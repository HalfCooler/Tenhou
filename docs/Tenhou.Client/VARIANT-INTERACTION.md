# 四川、国标牌桌交互草案

状态：四川血战到底 `sichuan-bloodbattle` 已接入共用图形牌桌，进入验收；实现与验证记录见文末。桌面锁定期间只进行协议、控制器与离屏检查，实际窗口点击尚未验收。国标仍使用文字牌桌，144 张牌山的最终摆放仍需截图试验；国标没有报听番种，不新增报听动作或立直棒标记。

## 当前已有的能力

- 四川现在通过有类型的 `VariantState` 投影到 `OnlineState`，使用 `LobbyView`、`OnlineTable`、`BuildTableScene` 和原有资源；下文保留交互设计及国标后续任务。

- `variant_table_view.cpp` 显示四家手牌文字、牌河、副露、花牌和分数，操作列表可双击或选中后执行。已有最小可用操作链路，缺的是直接操作牌面的体验。
- `network_protocol.cpp` 已把服务端 `actions` 转成 `OnlineAction` 和 `VACT` 消息，并维护动作 revision 和 pending。
- 服务器已实现四川换三张、定缺、血战和牌退场并继续其余玩家对局，及国标自动补花、八番起和。客户端只呈现服务器授予的动作。
- 直接复用立直的牌桌布局、牌面、背景、阴影、中央 HUD、候选按钮、最底部四个功能按钮、命中检测和单击出牌。`OnlineTable` 的状态入口与部分 HUD 分支需要参数化，通过变体状态适配进入同一套绘制与输入组件。

## 玩家看到的牌桌

采用四面牌桌：自己始终在下方，其他玩家按相对座位排列；中央显示轮到谁、剩余牌数、盘数和倒计时。自己手牌横排、牌河位于各家内侧，副露靠外。底部右侧放当前合法的吃、碰、杠、和、过按钮，结算和历史可展开查看。

> PS：常规对局逻辑和呈现直接复用立直的，例如牌面中央显示、牌山、牌河等，下方候选按钮（吃碰杠等）、最底下四个功能按钮也同样能够复用。

第一版以现有立直牌桌为基准，保留其视觉、点击习惯和可复用动画。先完成状态适配与公共呈现数据，再把两种玩法接入同一套组件。牌山继续显示；补齐总牌数、开口、前端已取数量和尾端已取数量后，复用牌山资源与绘制流程，移除王牌、宝牌与岭上牌保留逻辑。无需下发未来牌的实体。

> PS：与立直麻将不同的是，四川和国标没有王牌。这反倒更好办，因为只需要渲染牌山即可，这个逻辑同样能复用立直的。

144 张国标牌山需要每边 18 墩，超过原资源每边 17 墩的布局。实现时优先探索保留现有牌山尺寸与透视、平移复用牌山图块并调整间距的方案；以四个方向均不遮挡手牌、副露、中央显示为验收标准。具体位置和间距由截图验证后确定，不在本草案中预先固定。

>
> 和牌也和立直保持一致，按钮可以直接复用：“日语tsumo”或“日语ron”，以及取消。四川和牌后扣下手牌（就像立直流局未听一样），但保留和的那张牌在手切的那个位置明牌。
>
> 国标花牌优先采用 [lietxia/mahjong_graphic](https://github.com/lietxia/mahjong_graphic) 的资源。补花次数沿用三麻拔北的显示方式，以补的第一张花为牌面，右侧显示“×N”。发牌、摸牌、补牌遇花立即自动补，补到花继续补，不增加发牌完成后再轮流补花的阶段。补花的楷体浮字做一个即可。
>
> 四川和牌结算窗口：和牌玩家依次展示，复用立直结算。左上角显示玩家昵称。由于国标翻种较多，结算窗口的翻种显示用楷体小字显示。

定缺标记占用牌河显示首格，实际弃牌从后一格绘制；它是装饰层，不加入牌河数据、牌数统计或点击操作。此处只复用赤五图片作为花色图标，四川实际手牌仍没有赤宝牌。

已和玩家只扣牌并显示和牌张，停止回合高亮；服务端负责退场后不再摸打或付款，客户端不另行推导。圈风、门风直接复用立直的场风、自风显示，值由玩法和当前庄家适配，不能把“第几局”直接当成“第几家坐庄”。两种玩法不显示宝牌、振听、立直供托或本场棒；国标不新增报听或立直棒。

> PS：定的缺以赤宝牌的形式，放在每位玩家牌河的第一张上，灰色overlay，表示他定缺的花色。已和玩家只扣牌就行，不需要其他逻辑。圈风、门风仍可复用立直（场风、自风）。

底部四个自动功能沿用立直的样式、位置和含义：自动理牌、不鸣、摸切、自动和牌。换牌/定缺阶段暂停自动提交；不鸣不自动拒绝和牌，自动和牌也只执行服务端授予的动作。国标吃牌仍可能有多个顺子选择，这与是否有赤牌无关。

## 代码怎么接

### 1. 建立有类型的变体状态

新增 `variant_state.hpp/.cpp`，集中解析 `variant_state` 字符串字段，输出 `VariantState`、四家 `VariantPlayer` 和阶段枚举。统一验证牌 ID、座位、数字和分隔字段，绘制层不再到处 `stoi`。

- 服务器绝对座位转换成相对座位：`(absolute - local + 4) % 4`，自己固定为 0。
- 对手暗牌按 `hiddenN` 生成背面，绝不根据别人的副露或牌河推测手牌实体。
- `0..135` 使用现有牌面资源，四川、国标调用时禁用红五映射。
- `136..143` 单独作为花牌类型。当前 `TileVariant` 对大于 135 的 ID 返回背面，需登记八花图片并增加牌面适配；复用原有牌框、方向和计数布局。
- `winningN`、`retiredN`、`missingN`、`flowersN` 保留独立规则含义，通过呈现适配复用扣牌、装饰牌和拔北计数组件。

### 2. 先修动作数据，再做点击

当前 VSTATE 分支把实体牌列表拼在 `OnlineAction.label` 和消息中，`OnlineAction.tiles` 留空。图形交互前应把参数正规解析出来，显示文字不参与动作识别。

`dingque` 参数是花色编号，不是牌 ID，应有专用字段或明确的变体动作参数类型。其他牌组保持实体牌 ID。现有服务端 `VariantMatch.Unique` 按牌面合并动作，而 `MatchAction.Equivalent` 又要求实体 ID 精确一致；接图形输入前要修正这个组合：至少对 `discard`、`exchange` 保留可操作的实体组合，使点击哪张就发送、校验并消耗哪张。同牌面的另一张不能替代被点击的实体；选中换三张的三个 ID 也必须原样进入消息。碰/吃的等价候选可以继续在呈现层按牌面合并，但提交必须指向真实合法动作。提交保留原始 action index + revision，不用显示文字反推消息。

提取并复用当前 `LobbyView` 的悬停、拖动、单击提交、自动功能和 `ActionSelection`，变体适配器提供状态及合法动作。玩法专用的新增输入交互为换三张和定缺；多杠选择按下文修正共用组件。现有文字操作列表可作为开发诊断入口，正式牌桌按立直样式呈现。

多杠选择是共用控制器需要修正的现有差异：当前重建版 `LobbyView::Command` 的 5123 分支自动选择摸牌涉及的杠或首个合法杠，应改为打开 `kan` 候选。`ActionSelection` 当前仅支持吃/碰的手牌选择，要扩展具体杠动作的候选呈现和确认；按动作种类及完整牌组区分候选。立直、四川、国标共用此路径，候选不明确时不能自动替玩家决定。

换三张可从服务端所有合法组合中筛出包含当前选择的组合，候选牌取这些组合的并集。这样同花色、实体数量等限制都与服务端保持一致。选牌集合应排序后比较，提交时保留对应服务端动作索引。

输入按下时记录 revision，抬起提交时复核；有拖动则只理牌。新快照改变 revision、换盘或暂停时清理选择，防止鼠标停在原位置却提交下一窗口的动作。同样的检查覆盖按钮与键盘入口。

### 3. 共用牌桌、HUD 与输入组件

将 `OnlineTable` 的绘制入口提取为接收公共呈现状态的内部路径，现有立直入口继续通过适配调用。四川和国标通过 `VariantState` 投影到同一条路径，继续使用 `BuildTableScene`、`TableArtwork`、`PaintBuffer`、阴影、HUD 和命中矩形，不另建一套变体牌桌。呈现配置负责王牌/宝牌开关、牌山尺寸、定缺装饰、花牌计数与已和扣牌。

不要为了复用现有立直窗口而构造假 INIT、REACH 或 AGARI；特别是四川一次和牌不等于本盘结束。每种玩法决定自己的阶段切换，公共组件只消费呈现数据。

### 4. 动画和音效需要明确的公共事件

现有 VSTATE 适合静态交互，但不足以无歧义复原所有动画：

- 没有独立的摸牌实体字段，不能稳定区分新摸牌和手牌排序变化。
- 副露只有 `kind:tiles`，缺少来源座位及被鸣实体，无法可靠决定横放方向。
- 牌河已过滤被鸣走的牌；完整快照也可能同时包含出牌、副露、补花等多步变化。
- `history` 是最近若干条文字，不是唯一事件 ID；依赖它播放音效会在恢复时重复播报。

建议在保持现有快照和合法动作机制的基础上，增加公共呈现事件：单调递增 `seq`、`kind`、`actor`、可公开的牌和来源，以及当前玩家可见的 `drawn` 字段。首次连接/恢复使用快照对齐到 seq，之后只呈现未处理过的事件；序号缺口走快照重同步。序号、事件及快照的关联需要由服务端明确保证，避免重发和重连重复播放。

先接已有摸打、碰杠、和牌音效，统一经过 `ReplaySoundBank` 和音效音量；换三张、定缺、补花如无合适资源先用通用提示音。当前音频资源是立直客户端语音，不应当作已有四川方言或国标专用语音。私有摸牌事件只给当前视角，其他玩家只收到数量变化。

结算复用 `SettlementView` 的窗口、牌姿、分数变化和按条目展示的流程；服务端输出结构化条目：和牌顺序、玩家、和牌张、可公开手牌/副露、支付明细、番种与原因。现有 `SettlementYaku` 是立直役 ID，需扩展为带名称、分值和次数的通用显示条目；不把国标番种硬套成立直役 ID，不显示符或满贯档位。四川各家和牌记录保存为不可变收据，按实际次序呈现，正在继续的牌桌与结算浏览分开，结算窗口不触发下一盘屏障。

## 推荐实施顺序与完成标准
